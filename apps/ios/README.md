# Kelo for iPhone

The native iPhone app for Kelo. It does what the Android app does (`apps/android/kelo`, Kotlin + Compose, package
`chat.kelo.app`). It talks to the same self-hosted server (`src/assistant/server.py`). It is native only: SwiftUI on
iOS 17+, with one web view: the live browser screen (KeloWork/VncWeb.swift) draws the browser's X screen with noVNC 1.5.0 (MPL-2.0;
`KeloWork/Resources/vnc`, the same folder as the Android app's `assets/vnc`, licence in its LICENSE.txt, source and sha256 in SOURCE.md;
the app has no open-source notices screen). Its socket and bytes belong to the app (`KeloCore/Live/VncRelay.swift`, KE2E kept); the page
only draws, and anything that fails falls back to the JPEG picture. Sign-in pages for connectors open in the system browser
(`ASWebAuthenticationSession`), never inside the app.

It was first written on a Mac that had only the Command Line Tools; it now builds with Xcode 26.6 and runs in the iOS 26.5
simulator (checked against a pretend server, see "With Xcode" below). Layout:

## Building and testing

```sh
cd apps/ios/KeloCore && ./test.sh          # 293 tests
cd apps/ios/KeloUI   && swift build && ./test.sh   # all screens type-check; 317 tests (Shared, Shell, Chat, My, Work, Connectors)
python3 apps/ios/tools/gen_strings.py --check      # strings in step with Android (the server suite runs this and gen_version.py --check: server/tests/test_ios_generated_files.py)
```

`swift build` compiles every SwiftUI view against the **macOS** SDK. Code that only exists on iOS sits behind `#if os(iOS)` and
is therefore **not compiled until Xcode builds the app for iOS**: the QR camera (AVCaptureSession preview), the chat's camera
picker and speech input, BGTaskScheduler / UNUserNotificationCenter wiring, ASWebAuthenticationSession sign-in, UIKit keyboard
types, fullScreenCover and the navigation-bar modifiers. Expect a handful of small fixes on the first iOS build.

The Command Line Tools ship Swift Testing (`Testing.framework`), but not on the compiler's default search path, and they have
no XCTest. Both `Package.swift` files add the framework and rpath to the test targets only when Xcode is missing; `test.sh`
passes `-F <CLT frameworks>` to every target so the tests really run (a plain `swift test` would build a runner without Swift
Testing and silently run nothing). Once Xcode is installed, `swift test` works on its own and `test.sh` simply calls it.

## Words (20 languages)

The iPhone app uses the Android app's own texts. `tools/gen_strings.py` reads `apps/shared/strings/values*/strings*.xml` (the one home of the text; the desktop-only `strings_desktop*.xml` are skipped)
with `apps/android/tools/strings_res.py` (the reader the Android checks use) and writes `KeloShared/Resources/<lang>.lproj/
Localizable.strings` plus `KeloShared/Strings/R.swift`, whose names are Android's: Kotlin `stringResource(R.string.x, a)` is Swift
`L(R.string.x, a)`, `pluralStringResource(R.plurals.x, n, n)` is `P(R.plurals.x, n, n)`. Placeholders stay in Android syntax and
`StringFormat` fills them; plurals use CLDR categories (`PluralRules`, tested for all 20 languages). The app can be shown in a
language other than the phone's (first screen, 마이 → 언어), as on Android; Arabic flips the layout. After changing Android
strings, run `python3 apps/ios/tools/gen_strings.py` (or `apps/ios/Kelo/generate.sh`).

## What the app does (KeloUI)

- **Start**: language list → connect (scan the QR with the camera, paste the `https://host/#pair=CODE` link, or server address +
  access key; "Connect to this server?" names the host first; https only) → onboarding (your name, the agent's name) → app.
  The session lives in the Keychain (this device only); each screen's last data is cached encrypted (AES-GCM, key in Keychain).
- **Shell**: the floating header (round badge with the animated character, or the agent's photo with a green ring while it works;
  the name pill on its lower edge; a red news dot), centred, opening the work page; the bottom bar with 4 tabs (채팅, 다짐, 커넥터,
  마이) without fade or press highlight, tapping the open tab goes back to its start; sub pages take the whole screen; the
  "choose a model first" card; `GET /api/agent/status` every 3 s in the foreground drives the mood (offline, asking, stuck,
  listening, browsing, reading, working, thinking, done, asleep, idle); the app switcher shows a cover instead of the chat.
- **Character**: `KeloCharacterView` draws KeloCore's art in a SwiftUI Canvas inside a TimelineView, mood cross-fade 150 ms, calm
  moods at ~30 fps, Reduce Motion holds the still frame, `centerShift` keeps the body centred in the badge.
- **채팅** (KeloChat): history (kept and paged), replies followed with short requests (`/api/turns`), tool-progress chips,
  approval cards (allow / allow on this site / keep allowing in this job), payment cards (card sent with Face ID through the
  wallet), quick replies and follow-up buttons, attachments (photos/videos via PhotosPicker, camera, files via the document
  picker; 100 MB per upload checked before sending, progress), model chooser sheet + full model sheet (main and fallback on
  different providers, consent for unofficial providers), phone sign-in for subscription providers only when the server offers
  it, secure login entry (iOS AutoFill content types only, no password-app hint), report sheet, Markdown, voice input (Speech),
  stop, reconnecting notice. Since the catch-up with Android (CATCHUP.md): tool steps of one kind fold into one chip, one live
  browser card per reply and tab, the permission card for many items with its list, the task setup card (task_allow) and urgent
  cards, payment steps (approve in another app, one-time code, the page's PIN keypad live in the card), payment PINs released with
  Face ID, the morning briefing card, fill-in cards with the wallet's own card form and the PIN form inline (`AppModel.wallet`, set by
  the shell from KeloMy, so KeloShared and KeloChat need not import the wallet).
- **작업** (KeloWork, from the header): running now, waiting for you (approvals, stopped jobs, held follow-ups), watchers, upcoming
  (agenda by day), past with filters; task / job / watcher / browser tab pages (a finished task or job: Save as skill); schedule editor in plain words (date, time, repeat
  with weekday circles, end, history, run now, pause) — no cron text anywhere; the live view of a browser tab (WebSocket frames,
  polling fallback, take control, taps / scroll / keys, quality by network).
- **다짐** (KeloWork): suggestions, in progress, done; add / edit sheet; goal page with plan, metrics, schedules, documents, log.
- **커넥터** (KeloConnectors): exactly the rows the server sends, grouped like Android (home / all / search / group chips); detail
  page with each connect method: device code, MCP sign-in in the system browser (ASWebAuthenticationSession), mail, API key forms,
  Google (calendar accounts, review note, service account), site logins, disconnect; operator app settings for the owner.
- **마이** (KeloMy): profile, agent (name, picture), model + fallback, usage, devices (pair another phone: QR via CoreImage),
  resources (the server machine's capacity as numbers), keychain (vault) and its log behind Face ID / passcode, documents (only
  your uploads; viewer, upload, delete), notifications ("Kelo가 먼저 알려주기", follow-up timing, hours), permissions and approval
  rules/history, records (journal, look-back, learned rules, skills to approve), language, wallet (behind Face ID: cards, limits, payments, pause,
  add card), operator pages (owner only), server update (owner only: newer version and its notes, update with progress through
  the server's restart, the result, go back, nightly auto-update; `KeloServerUpdateShotsTests` with `KELO_SERVERUPDATE=1`), sign out.
- **Card scanning**: [카드 스캔] under the card number (add card, a card fill-in card, typing a number again) uses VisionKit's live
  text (`DataScannerViewController`, on the phone only; the camera permission the app already has). Number and expiry only, never the
  CVC; frames must agree (KeloCore `CardScanRules`). No button where VisionKit cannot scan (the simulator).
- **Morning briefing settings** (마이 → 알림): time, offset, early open, sections (turning the weather on asks for location "while
  using the app"; `PhonePlace` sends the phone's location, precise or approximate as the owner chose, whenever the app is opened;
  without one a quiet line offers to allow it), quiet days, what it reads (one switch per calendar and mail account), weather
  service and keys, "Get one now"; weekday and weekend message hours with learned windows and suggestions.
- **Phone data on iPhone**: calendar (EventKit: read, and with "Also allow adding and editing events" add / change / delete in the
  picked calendar after an approval card), contacts (Contacts framework, read) and the phone dialer (after an approval the phone
  app opens with the number filled in; a notification when Kelo is in the background). All use the same server endpoints as
  Android (`/api/phone-calendar`, `/api/phone/contacts`, `/api/phone/dialer`, `/api/phone/tasks/claim` + `/result`). EventKit's
  text identifiers are mapped to stable whole numbers on the phone (`PhoneIdMap`), because the server names events by number.
  SMS, call log, notification access and Health do not exist for apps on iPhone and are not shown (Health is not in the Play
  build either).
- **Share sheet**: the `KeloShare` extension ("Send to Kelo", localized from Android's `share_label`) leaves the shared text and at
  most one file in the App Group `group.chat.kelo.app`; the chat takes it when it shows (text into the draft, the file attached).
  The App Group needs a signing team that has it (simulator builds without signing simply never see a share).
- **Notifications**: real push through APNs when the operator's key is set (see Push); otherwise, and as the fallback, the app
  checks `/api/notifications` every minute while open and in background app refresh (`chat.kelo.app.refresh`), posting local
  notifications. Tapping a push or a local notification opens the right place.

- Wallet: cards are sealed per phone, so a card added on another phone must be typed again here (the card page offers that). The

- Push is built (see Push) but only tested against a pretend APNs; the first real push needs the operator's key.

## What is done (KeloCore)

- **API models**: 108 `Codable` structs for profile, goals, devices and pairing, stored messages, providers and models,
  conversation summary, agent status (with `running[]`), tasks and task detail, approvals (pending, history, rules,
  answers), schedules (with runs, archive / restore and schedule rules), watchers (with dry runs and events), browser tabs,
  live tickets and control, workers (with detail, report and lines), journal, reflection (learned rules), avatar,
  notifications, follow-up settings, connectors catalog (with key forms, mail, OAuth device flow and OAuth apps), keychain
  (vault) items and log, wallet metadata (cards without numbers, limits, payments, notifications, e2e blob, pause), usage,
  resources, uploads and push status.
  - The field names come from the server's API comment blocks (`server.py`: turn events, AGENT SCREEN, LIVE VIEW, PUSH,
    WORKERS, WATCHERS and FOLLOW-UPS APIs; `followups.py`) and from the Android models.
  - Decoding is lenient, like the Android client's kotlinx settings. A missing, null or mistyped field takes its default.
    An id that comes as a number reads as text, and a number that comes as text reads as a number. A list leaves out entries
    that lack their id.
- **KeloApi** (URLSession, async/await):
  - It sends `Authorization: Bearer` (left out for `POST /api/pair`) and `Accept-Language` (`AcceptLanguage.build`, the
    same rules as Android `core/AcceptLanguage.kt`).
  - Errors are `ApiError`: the string `detail` of a JSON body, else "HTTP n". A 401 calls `onUnauthorized`. An answer that
    is not JSON counts as "server not reached".
  - It handles uploads and downloads, cancels with the Task, and keeps no cookies or disk cache.
  - `Endpoints.swift` has typed calls for every screen.
- **Chat replies**: `TurnFollower` is the app's main path. It starts with `POST /api/turns`, then repeats
  `GET /api/turns/{id}?after=n&wait=20` and retries passing failures from the same place, with the same backoff and
  reconnecting notice as Android. Cancelling sends `DELETE /api/turns/{id}`.
  - `talkStream` / `sseEvents` read the SSE stream of `POST /api/talk`, through a spec-following SSE parser (CR / LF / CRLF,
    multi-line data, comments).
  - Quick tunnels drop streams, so the app follows replies with short requests, as Android does.
- **Turn events**: every type the server documents is decoded: thinking, text, tool_started / result, approval_request
  (payment, card, lines, site, remember flags, expiry), browser, browser_control, browser_check, card_needed, payment_auto,
  step_limit, fallback, retry, done, error, followup and worker. Unknown types are ignored.
- **Pairing**:
  - `PairingLinks.parse` reads the link `https://host[:port]/#pair=CODE`, which is also the QR payload, by the same rules as
    Android: code length 16 to 128, percent-decoding that keeps `+`, no user info, query or fragment, host lowercased, and
    https only except local hosts in debug builds.
  - `PairingClient.pair` exchanges the one-time code for this device's token (`POST /api/pair {code, name}`).
    `checkKey` covers the server address + access key path.
- **Rules ported from Android**, each with its tests:
  - follow-up action mapping and HTTP calls
  - the work badge, timeline, agenda and watcher order
  - the character mood priority (`AgentActivityRules.mood`), status lines, turn kind and browsing / stuck / finished checks
  - card number, CVC, expiry and masking, card face palette and preview
  - connector sections, featured home view, groups, reconnect, initials and hue
  - live view geometry, messages and reconnect machine
  - cron builder, day groups, relative time, learned-rule grouping and chat history trimming
- **The Kelo character**: `gen_kelo_art.py` turns the 11 SVGs into `KeloArt.swift`: 268 shapes and 33 animations, checked
  identical to Android's `KeloArt.kt`.
  - `KeloMotion` plays the CSS keyframes as pure math: frame time in, per-group affine transforms out. It covers timing
    functions, alternate, delays, transform origins, fill colour and opacity.
  - It also has the reduced-motion still frame, the cross-fade and the calm-mood frame step.
  - Its tests mirror Android's `KeloMotionTest`.

## What needs Xcode (step by step)

1. Sign in to the App Store with an Apple ID (App Store → Sign In), then install **Xcode** (≈ 15 GB) and open it once to accept
   the licence and install the iOS platform (Xcode → Settings → Components → iOS).
2. `apps/ios/Kelo/generate.sh` (regenerates the strings and `Kelo.xcodeproj`; the committed project also works as is).
3. Open `apps/ios/Kelo/Kelo.xcodeproj`. Xcode resolves the two local packages by itself.
4. Target **Kelo** → Signing & Capabilities → Team: your Apple ID (Personal Team is enough to run on your own iPhone). Keep the
   bundle id `chat.kelo.app`, or change it if Xcode says it is taken (e.g. `chat.kelo.app.<yourname>`).
5. Plug in the iPhone (or pick a simulator), turn on Developer Mode on the phone (Settings → Privacy & Security), press Run.
6. First iOS build: fix any small errors in the `#if os(iOS)` code (listed under Building and testing), which `swift build` on
   macOS could not compile.
7. Then: run on a device, check every screen at 320 / 375 pt widths in a long language (de, ru) and in Arabic, and add UI tests.

## Push: direct APNs (option B, built)

The iPhone gets real push through **Apple's push service (APNs) directly**: no Firebase or other SDK in the app (the App Store
privacy answers and the privacy page say the iPhone app has no external SDK, and that stays true).

### How it works
1. The user allows notifications (the existing ask: `NotifyAsk.enable`, 마이 → 알림, `NotifyPermission.request`). Then the app calls
   `registerForRemoteNotifications()`, at every start too (`KeloBackground.run` → `PushRegistrar.sync`), because iOS may change a token.
2. `KeloAppDelegate` (KeloShell, plugged into `KeloApp` with `@UIApplicationDelegateAdaptor`) receives the device token. The app
   sends it to **its own server**: `POST /api/push/register {token: <hex>, platform: "ios-apns", environment: "production"|"development"}`.
   `environment` is the app's `aps-environment`: `development` for an Xcode / debug run, `production` for TestFlight and the App
   Store (builds with no embedded provisioning profile; `PushRules.environment`). One token per device; a new one replaces the old.
3. The token is taken back (`DELETE /api/push/register`) at sign-out (`AppModel.onSignOut`, also when this phone is removed in
   마이 → 내 기기) and when notifications are turned off in iPhone Settings. The server also drops it when the device is
   removed, and when Apple answers 410 Unregistered or 400 BadDeviceToken.
4. **What triggers a push is the server's own logic, unchanged** (`activity.py` → `PushClient.notify`): the same notifications as
   Android (a reply or approval nobody was watching, payments, schedules, watchers, proactive, follow-ups, a phone's waiting task).
   Nothing about quiet hours or "who is watching" is duplicated in the app.
5. A copy that does not hold the key sends through the **operator's push broker** (`POST /broker/push/send`), which now also takes
   `"apns": [{token, environment}]` and answers `"apns_results"`. The operator's own copy sends straight to Apple.
   The sender (`push.py` `Apns`): HTTP/2 to `api.push.apple.com` (production) or `api.sandbox.push.apple.com` (development),
   `POST /3/device/<token>`, ES256 JWT provider token (cached 40 minutes, minted again on `ExpiredProviderToken`), headers
   `apns-topic` (bundle id), `apns-push-type: alert`, `apns-priority: 10`, `apns-expiration` (+24 h), `apns-collapse-id`.
   410 and BadDeviceToken drop the token; 429 and 500/503 are retried with backoff; other errors are logged by Apple's reason only.

### What the push carries (and why)
```
{"aps": {"alert": {"loc-key": "kelo_push_update"}, "sound": "default", "content-available": 1},
 "type": "task_done", "id": "41", "task_id": "9"}          // only kind and ids, like the Android FCM data message
```
- **Choice: a generic localized alert plus `content-available`, no Notification Service Extension.** The banner text is a key
  (`kelo_push_update`, "Kelo has an update") that the phone looks up in its own `Localizable.strings` (20 languages, generated by
  `tools/gen_strings.py` from `tools/push_strings.json`), so no words of ours or of the user travel through Apple, and the banner
  appears even when the app is force-quit (a silent data-only push would not).
- When iOS also wakes the app (`content-available`, best effort and throttled by iOS), `didReceiveRemoteNotification` runs the
  normal `NotificationCheck` against the user's own server, posts the detailed local notification and takes the generic banner
  down (`PushRules.isBarePush`). If iOS does not wake the app, the banner stays, a tap opens the right place
  (`PushRules.target`, the same mapping as local notifications), and the next background refresh or app open fetches the details.
- Why not a Notification Service Extension: it would give the real text on the banner even when the app is not woken, but it
  needs a new target, a shared Keychain access group holding the session (a migration of every signed-in phone's session) and
  its own networking, and it cannot be tried without a real device and key. It is the next step if the generic banner is not enough;
  the payload would not change (add `mutable-content: 1`).
- The body never holds personal text: `check_data` refuses anything but kind and ids (on the copy and again on the broker).

### Setting it up (the owner, once)
1. Apple Developer → Certificates, Identifiers & Profiles → **Keys** → **+** → name it, tick **Apple Push Notifications service
   (APNs)** → Continue → Register → **Download** the `.p8` (only once; keep it safe). Note the **Key ID** (10 characters) and your
   **Team ID** (Membership details; Kelo's is in `project.yml` as `DEVELOPMENT_TEAM`).
2. Identifiers → `chat.kelo.app` → tick **Push Notifications** capability → Save. Provisioning profiles then regenerate (Xcode's
   automatic signing / cloud signing does this by itself).
3. On the **main (operator) server** only, set these in its environment (never in git, never in logs) and restart it:
   - `KELO_APNS_KEY_FILE`: the path of the `.p8` file on the server's disk (the key is read from there, never stored in the database)
   - `KELO_APNS_KEY_ID`: the Key ID
   - `KELO_APNS_TEAM_ID`: the Team ID
   - `KELO_APNS_TOPIC`: the bundle id; optional, default `chat.kelo.app`
   Check with `GET /broker/push/status` → `{"push": true, "apns": true}`. Without the variables iPhone pushes are skipped quietly and
   the app keeps its polling path. Other people's copies need nothing: they send through the operator's broker.
4. Build and install as usual (`aps-environment` is in `App/Kelo.entitlements`, generated from `project.yml`; the `remote-notification`
   background mode is in the Info.plist). TestFlight and App Store builds are signed for production APNs by Apple.

### What was tested, and what was not
- Server: `tests/test_push.py` against a pretend APNs (JWT signature, headers, host per environment, payload, 410 and BadDeviceToken
  removal, 429/503 retry, expired provider token, missing variables or key file, the operator's copy and a copy through the broker, no
  text or token in logs). iOS: unit tests for the token, registering, unregistering, sign-out, the environment and tap routing.
- **Not tested: a real push to a real iPhone.** Nothing was sent to Apple (no key was available). Not seen on a device: the
  banner, the wake-up replacing it, the real `aps-environment` of each kind of build, and HTTP/2 against Apple's servers (the
  server uses `httpx[http2]` with the same pinned-IP, https-only fetch as every other call).

## Earlier options, for the record

- **A. Firebase Messaging iOS SDK**: simplest given the existing broker, but a third-party SDK in the app. Not chosen.
- **C. No push**: foreground polling, a `BGAppRefreshTask` check and local notifications. Kept as the fallback.

## Signing and installing

- **Free Apple ID** (Xcode, Personal Team):
  - It installs on your own iPhone over USB or Wi-Fi, and the app expires after **7 days**, so reinstall from Xcode.
  - At most 3 apps per device.
  - No push (the `aps-environment` entitlement needs the paid program), no TestFlight, no App Store.
  - Turn on Developer Mode on the iPhone (Settings > Privacy & Security).
- **Apple Developer Program** (paid, yearly): a one-year profile, push (APNs key), TestFlight for testers, and App Store
  distribution.
  - The bundle id `chat.kelo.app` must be registered under that team.
  - A Keychain access group is needed if a Notification Service Extension shares the session.
  - Once the app has an App Store id, add `KeloAppStoreID: "<id>"` to the app's Info.plist properties in `project.yml`: the
    required-update screen (the server's `ASSISTANT_MIN_APP_IOS`, compared with CFBundleVersion) then opens Kelo's own App Store
    page (TestFlight copies: its TestFlight page) instead of an App Store search for Kelo.
- **Self-hosted servers**: each person's server has its own address. Release builds reach it over https only (App
  Transport Security). Plain http is accepted only for localhost / 127.0.0.1 in debug builds (`ServerAddress.isAllowed`).
  Tailscale (`*.ts.net`) and the user's own Cloudflare domain both give https.

## Notes for whoever continues

- Do not wrap the web app or add a WKWebView. Every screen is native SwiftUI.
- Do not copy feature names or wording from other assistant apps. Use Kelo's own words in the String Catalog.
- Never log or print tokens, pairing codes, card data or typed live-view text. The client keeps none of them beyond the
  call that needs them.
- The Android app is the reference for behaviour. When the server's contract changes, update the table in
  `tools/gen_models.py`, regenerate, and extend the tests.
